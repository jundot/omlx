## Audit: MoE expert streaming engine (analysis only, no code changes)

Audited `omlx/patches/expert_streaming/` (~7.7k LOC) + Swift/webUI integration.
Branch: `fase-0/routing-capture`, tree clean.

### Central finding
The stated product requirement — *detect machine RAM and scale residency
(more RAM → more experts cached, not streaming)* — is **not implemented**.
- `residency.py` estimates model bytes only; no RAM detection.
- `_get_budget_bytes()` (`__init__.py:41-63`) returns **0** by default
  ("page-cache only"). Same in `engine_pool._streaming_budget_bytes:520`.
- `model_settings.expert_streaming_budget_gib` defaults to `None`.
- RAM is used only as a **boolean gate**: `force_streaming(ceiling)`
  (`residency.py:37`) flips streaming ON/OFF vs the enforcer ceiling.
  A 512 GB and a 48 GB machine get identical budget (0) once streaming is on.
- No RAM-derived sizing anywhere; `shard_bank.py`/`warmer.py` use only
  `SC_PAGESIZE`. Autotune sweeps a fixed grid (`--budgets 0,2,4`), offline.

### The `last_future_wait` flake — important, do not "fix" by raising thresholds
`test_last_future_wait_isolates_tail` passed alone, failed in the full suite.
Root cause is real, not noise: `last_future_wait_us` is sampled on the
iteration where `len(window) == 1`. On the process-wide 16-worker pool all 4
runs execute in parallel, the 3 fast ones complete and are popped first, so
the slow run is the one still in flight when the window shrinks to 1 — and the
"tail" legitimately absorbs the whole 50 ms sleep (measured 60 ms). With a
cold pool the reads serialize and the tail is ~0, which is why it was green in
isolation. **Fix applied**: monkeypatch `shard_bank._run_io_pool` to a
1-worker executor for that test. Do NOT widen `_RUN_IO_QD` to 1 — every
iteration would then have `len(window) == 1` and `tail["count"]` becomes 4,
breaking the count assertion.

### Design constraint for front A (do not re-derive)
The residency budget **cannot** derive from the memory-guard ceiling:
`force_streaming(ceiling)` consumes the ceiling and `_entry_runtime_resident_
size` compares the result against that same ceiling, so a ceiling-derived
budget is circular and non-monotonic under vm_stat jitter. Derive from
**total/available RAM** instead.

**A4 (pin accounting) MUST land before A5 (pins on by default)** — wired pages
are invisible to `proc_pid_rusage`, so without accounting the enforcer cannot
see pins and low-RAM machines can be pushed into swap.
