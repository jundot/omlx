# Fit-Gap: DAU workflow walkthrough on `.12` + `.13` (2026-11-16)

Full click-through of the Cluster tab in Assistant **and** Manual mode on the
live 2-Mac cluster (`.12` origin, `.13` paired, build `60d74f29`), driven
through the in-app browser against `http://172.16.1.12:8000`. Evidence for
every finding was read from the real DOM/network, not guessed. `.11` (GPU
reserved for other work) and `.14` (reassigned) were never touched.

## What was walked

**Assistant flow, end to end (works):**

- „Find and start a setup" → hardware measurement → recommendation →
  model-bound measurement → plan (`dev-1.5b`, the only checkpoint the 96 GiB
  pool can split; honest 32K/saved-tier/2-Mac plan, coordinator `.13`) →
  „Start setup" → `applying → staging → loading → ready` in ~15 s.
- Ready card: endpoint `http://172.16.1.13:8000`, Copy URL, Open Chat,
  Connect agent, Refresh, Stop cluster.
- **Stop cluster** → session strip „Last deployment … Stopped", endpoint link
  hidden, „Start again" offered. **Start again** → `applying → starting →
  loading → ready`, same endpoint. Round-trip verified twice.
- Reload after ready: the card returns to the session strip
  („Last deployment dev-1.5b · 32.768 tokens · MacStudio-von-Andreas-2 ·
  Running") — resume works.

**Manual flow:** partially — see Gap 1. The device cards, checks list and
the active/plan sections contain complete, well-labeled content (verified by
forcing the sections visible; see Gap 1 for why that was needed).

## Gaps

### 1. P0 — Manual wizard sections freeze after first render (resolved: automation artifact)

In the embedded test browser the Cluster tab in Manual mode sticks on
„**Looking for other Macs…**" forever: no device cards, no checks, no plan.
`wizardState()` computes correctly (`active`), the scheduler is alive (mode
buttons update), there are no console errors with the fixed build, and the
served JS is verified current (no cache). The `x-show` effects of the wizard
sections evaluate once at init and never re-apply; the assistant card's
screens update on some loads and freeze on others.

Reproduced 5/5 loads on today's build and on the full yesterday build
(JS+template). **User verification 2026-11-17: the device cards appear in the
real browser** — the freeze is an artifact of the automation browser, not a
product bug. Closed. (If it ever shows up in a real browser, the diagnostic
trail above is the starting point.)

Related real bugs found under this symptom (both **fixed**, commit
`58e0b840`): the rebase merge `9705a8e8` dropped `cudaGuideOpen /
cudaGuideOs / cudaGuideCopied` from `clusterV2Wizard`'s data while the
upstream #5163 CUDA guide template kept binding them (every page load threw
„ReferenceError: cudaGuideOs is not defined", warn + delayed re-throw), and
`assistantFailureOpen` was declared inside the `assistant` sub-object while
template and methods use it top-level (one throw per fresh load).

### 2. P1 — Stale join record ghosts the page (fixed, `00f49391`)

After unpairing `.11`, `.12`'s join-session still reported
`state: approved, coordinator: 172.16.1.11:8000`. Effects on every page load:

- toast „This Mac joined MacBook-Pro-von-Andreas's cluster."
- in Manual mode a full panel „**THIS MAC IS JOINING** / Joining
  MacBook-Pro-von-Andreas's cluster / Cancel join".

A DAU sees a join that is not happening. Root cause fixed: approvals now
store `coordinator_node_id`, and `snapshot()` retires an approved attempt
whose coordinator is no longer a paired device (address fallback for old
records, fail closed on read errors). The stale `.12` record reconciles on
the first join poll after the app restart with the new build.

### 3. P1 — Open Chat lost the model after a reload (fixed, `7e9b845d`)

After a page reload, „Start again" → ready card → **Open Chat** linked to
`/admin/chat` **without** `?model=`: `modelOptions` is only loaded by
`startAssistant()`, never on the resume path. The chat then silently selects
its default model — measured: GLM-5.3-Flash-MLX-4bit on `.13` while the
running cluster served dev-1.5b. A DAU would chat with the wrong model.
Fix: `runAssistantResume()` now `ensureAssistantModels()` first.

### 4. P1 — Open Chat → login dropped the deep link (fixed, `7e9b845d`)

First Open Chat to a coordinator the browser is not signed in on: 302 to the
login page, and after signing in you land on the **dashboard** — chat URL and
model param lost. Fixed by carrying `?next=` on the unauthenticated-HTML
redirect, honouring it on the signed-in login page, and returning there after
login (path-only, `//` rejected). **Needs an app restart on `.12`/`.13` to go
live** (server-side code).

### 5. P2 — Stale deployment records read as a configured cluster (fixed, user decision 2026-11-17)

Manual mode showed „**CLUSTER CONFIGURED** / GLM-5.3-Flash-oQ2e-mtp / …
placement is saved, but no model weights are resident" — this morning's
leftover, while the actual cluster ran dev-1.5b. Decision: rename +
timestamp. The registry envelope now carries a `saved_at` stamp per
deployment (set on first save, kept across re-approvals, dropped on remove,
tolerant when old files predate it), the deployments API reports it, and the
not-loaded card reads „**SAVED SETUP** / Not loaded / … Saved <date, time>".
No invented age: without a stamp the line stays away.

### 6. P2 — „Not started" next to a running cluster (fixed, user decision 2026-11-17)

On reload with a ready cluster the card eyebrow said „Set up this cluster /
Not started" while the strip below said „Last deployment … Running". Decision:
the session is the headline. With a persisted session the card title becomes
„Cluster running" / „Cluster stopped" / „Setup applied" (English in every
locale — the assistant namespace is deliberately untranslated), the subtitle
carries the session's model/context/coordinator line instead of the pitch,
and the „Not started" flow chip hides while the session owns the card.

### 7. P3 — `.14` is offered as „Pair / Join" in the manual device list

Correct product behavior (any nearby Mac is pairable), but during this
validation phase `.14` is locked and must never be paired — the walkthrough
respected that.

### 8. P1 — Manual activation died in the SSH preflight (fixed, `4b81598f`)

User walkthrough 2026-11-17 on `.12`+`.13`: Manual setup → Change model →
unload → choose dev-1.5b → **Activate cluster** failed with
„SSH preflight failed for 2dd48599: ModuleNotFoundError: No module named
'omlx'", while the assistant had started dev-1.5b on the same Macs minutes
earlier.

Cause: the manual plan's hosts carried no recorded interpreter (the browser
fills `python_executable` from the cluster-check probes, which a fresh page
has not run), so the preflight and the rank launch argv fell back to the
coordinator's `sys.executable` — the runtime-venv path that exists on the
peer only by accident and cannot import oMLX without the PYTHONPATH only
the worker shim sets. The assistant worked because its deployment hosts
record the peer interpreter from the measurement. A host without a
recorded interpreter now runs `~/.omlx/bin/omlx-cluster-python`
(`DEFAULT_REMOTE_PYTHON`, the documented cross-Mac contract) in both the
preflight and the rank argv. Confirmed fixed by the user's re-run on build
`4b7b8106` (2026-11-17): the manual activation loads at „Load weights", and
the live registry shows `dev-1.5b-8f8dc79192f4` with a `saved_at` stamp and
rank 0 `ownership: loaded, phase: ready`.

## Positives worth keeping

- The one-action Assistant path works end to end, including stop/start-again
  and reload-resume, with honest refusals and no invented numbers.
- Device cards (name, chip, `IP · C/G · UM/SSD`, role, link, version) and the
  checks list (self-healing rows, honest RDMA fallback note) are clear.
- Stop/start of the real cluster is fast and reversible (~15 s each way).
