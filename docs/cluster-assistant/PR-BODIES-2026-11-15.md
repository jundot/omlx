## F1 · `fix/local-only-load` — `fix/models: add ?local_only=true to the model load route`

Measured: 5 files, +271/−22 — 107 code, 164 tests.

<!-- ===== BEGIN PR BODY ===== -->

## Summary

`POST /api/models/{id}/load` had no way to say "this Mac only". On a Mac that is
part of a cluster deployment of the same checkpoint, the load adopted the
registry's deployment, so live admission was compared against rank 0's shard
instead of the whole model, and the resulting engine was reported as this Mac's
own single-Mac load.

This adds an optional query flag, `?local_only=true`, which:

- ignores a registry cluster deployment of the checkpoint, so the load either
  fits the local memory ceiling or is refused with `507` here;
- unloads an already-loaded distributed engine for that checkpoint, or refuses
  while it is busy, instead of reporting it as a local load;
- prices the checkpoint's offloaded table bytes (Engram / PLE) into local
  admission, so a table-offloaded model is not admitted as if fully resident.

Default behaviour is unchanged; without the flag the route behaves exactly as
before.

The PR also stops rewriting a failed *deployment* as the VLM → LLM fallback: the
deployment error is the cluster's verdict, and mlx-lm cannot load the vision/
PLE tensors anyway. Both changes come from the same defect — a cluster
deployment leaking into a local load — and the fallback was the reason the leak
surfaced as a misleading mlx-lm error rather than a clear cluster refusal, so
they are kept together.

## Validation

- `uv run pytest tests/test_engine_pool.py tests/test_cluster_engine_pool.py tests/test_admin_load_errors.py -q` → **244 passed**.
- New regression tests: a local-only load ignores a registry cluster deployment
  and plans from the full checkpoint; a loaded distributed engine is unloaded
  (and refused while busy); table-offload bytes are included in local admission;
  the admin route forwards the flag and skips the "already loaded" shortcut.
- The cluster deployment is a fake registry entry, so the run needs no cluster
  hardware. M5 Max 128 GB, macOS 27, Python 3.13.
- No behaviour change on the default path: the existing engine-pool and admin
  load-error tests pass unchanged.

Test fixtures now use documentation-range addresses only.

## A1 · `feat/cluster-assistant-plan` — `feat(cluster): Cluster Assistant — measure, recommend, plan (1/3)`

Measured against the integration base: 62 files, +22 884/−79 — 11 909 code,
10 172 tests, 693 i18n lines (+63 keys × 11 locales, additive only), 110 docs.

<!-- ===== BEGIN PR BODY ===== -->

## Summary

First of three slices of a cluster mode inside oMLX: run one model that does not
fit a single Mac across 2–4 Apple Silicon Macs connected by Thunderbolt, and let
the app decide which Mac is the coordinator instead of "whichever Mac opened the
dashboard".

This slice is **read-only**. It measures, recommends and plans; it starts
nothing.

- **Measurement** (`omlx/cluster/assistant/measurement.py`) turns oMLX's own node
  budgets, performance profiles and link measurements into per-Mac facts. A
  measurement that did not happen stays missing — no zero, no nominal rate, no
  estimate. A model that lives only on another Mac is measured from that Mac's
  inventory and layout.
- **Persisted measurements** (`state.py`): one bounded, atomic JSON file under
  `<base_path>/cluster/`, one documented staleness/mismatch rule (15 minutes,
  node set, model identity, MTP capability).
- **Election** (`election.py`): a pure decision over measured facts. It uses the
  **fewest Macs that fit**, ranks by measured critical stage, then headroom, then
  fewer hops, then the coordinator preference, and never falls back to the local
  Mac. Rank 0, coordinator and endpoint are co-located; pipeline parallelism
  only, tensor parallelism is refused.
- **Recommendation** (`recommendation.py`): "which model should these Macs run?"
  over the whole catalogue, from the hardware half of a measurement. It also
  answers with a single node when the model fits one Mac.
- **Resource policy** (`policy.py`): context, table offload (Engram / PLE),
  routed-expert offload, memory-guard tier, microbatch and admission percentile
  are carried as one object through measure → recommend → plan. The plan shows
  every lever and the experts-vs-context trade as an explicit choice, and never
  drops context silently.
- **Topology** (`topology.py`): a 3/4-Mac plan needs a connected line through its
  rank order; a missing pair is refused with the exact cables named, and the
  2-Mac fallback is offered only with explicit consent, which salts the plan
  signature.
- **UI**: one assistant card inside the existing Cluster tab that renders the
  backend's answer, shows exactly one action per refusal, and derives no plan,
  rank order or coordinator itself. The card stops at the plan.
- **API** under `/admin/api/cluster/assistant`: `POST /measure`,
  `GET /status`, `POST /recommend`, `POST /plan`, and
  `DELETE /models/{node_id}/{model_id}` so a recommendation that needs space can
  name the Mac and model (the assistant never deletes anything by itself).

`CLUSTER-ASSISTANT.md` documents the feature and the API.

### Dependencies and merge order

prerequisites merged first, and it does not stand alone:

## Summary

Second of three slices: it turns the plan from 1/3 into a running cluster, and
lets the user stop it and tune it.

- **Apply** stages the model to the **selected** Macs only, writes the approved
  resource policy (context, table offload, expert offload, tier, microbatch) on
  each of them before staging, and refuses a plan that drifted since it was
  approved (`409 plan_mismatch`, one action: `plan`). A Mac short of disk is
  freed automatically by the documented rule — only a model that Mac listed,
  never the checkpoint being deployed, never the last complete copy, largest

  starts this Mac as rank 0.
- **Operations** are persisted (atomic, fail-closed, interrupted → failed), are
  forward-only, and are cluster-wide single-flight: each origin asks the elected
  coordinator whether an apply/start is already running before creating one.
- **Stop and resume.** `POST /stop` unloads the deployment on the coordinator and
  hides the endpoint. After a reload, `GET /session` resumes the newest ready
  start (or applied apply) with its frozen plan inputs and stopped flag — no key,
  no SSH target, no secret.
- **Tune.** A sampler sweep and the MTP on/off/depth configurations are measured
  and the winner is saved as a preset per (model, node configuration); Start
  replays it before activation. `POST /tune-redeploy` runs the same as a
  background job and stops the cluster first.
- **Also in this slice**: diagnostics (only a start reports it), a read-only
  network preflight (prints the exact commands, executes nothing), the
  post-`ready` performance measurement behind a setting that is **off by
  default**, model search, the "Open Chat" handoff that preselects the model in

- **UI**: apply/ready/stop/restart, the progress rows and the chat handoff inside

## A3 · `feat/cluster-assistant-run-local` — `feat(cluster): Cluster Assistant — run on one Mac (3/3)`

Measured against 2/3: 13 files, +4 268/−16 — 2 231 code, 2 019 tests, 18 docs.

<!-- ===== BEGIN PR BODY ===== -->

## Summary

Third of three slices: when the model fits **one** Mac, do not build a pipeline
— run it on this Mac.

- **Run on this Mac.** `POST /admin/api/cluster/assistant/run-local` starts a
  background job (`GET …/run-local/{job_id}`, one run at a time) that proves the
  model fits **this** Mac at the requested context with the same admission rule
  the planner uses, replays the saved tuning preset for this Mac's configuration,
  loads the model through this Mac's own engine pool and verifies that the pool
  reports it loaded. A too-large context is refused with
  `context_too_large` / `adjust_model_or_context`; nothing that fits is
  `insufficient_memory` / `choose_smaller_model`. It never silently uses a
  smaller context.
- **Readiness and stop.** One tiny completion is required before the run is
  reported `ready`; `POST …/run-local/{job_id}/stop` unloads it.
- **Tune locally.** `POST …/tune-local` runs the sampler sweep and the MTP
  on/off/depth configurations on this Mac (write settings, unload, load
  local-only, one real completion each), leaves the winner loaded and saves one
  preset, so a later "Run on this Mac" replays it.
- **UI**: a "Run on this Mac" card in the existing Cluster tab, offered only when
  the recommendation's single-node answer names this Mac.

Everything here is loopback with this Mac's own key — no SSH, never another Mac.
