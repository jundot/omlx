## P0/P1 — blocks the 2-Mac baseline / DAU

### 1. Join approval code input appears only after a manual refresh

- **Symptom:** A joining Mac is shown as `wants to join`, but the six-digit
  input/replace control is absent. A full page refresh makes it appear.
- **Cause:** `wizardState()` checked the local `stage` shortcuts
  (`checks` / `purpose` / `plan`) before `pendingApprovals()` / `joinActive()`.
  The device label updates through `devicesPayload` at 1 Hz, while the pairing
  section stays hidden because the wizard is still `checks`/`purpose`.
- **Status:** **source fixed, installed in the helper4 build.** The pairing/join
  block now comes before the stage shortcuts (after the active deployment
  panel) in `apps/omlx-web/omlx_web/static/js/cluster_v2.js`. The installed app
  contains it; the live click-through was not repeated after the rollout.
- **Tests:** `apps/omlx-web/tests/ui/test_cluster_v2_wizard.py`
  (`test_pending_join_wins_over_stage_shortcuts_in_wizard_state`,
  `test_incoming_join_opens_the_code_form_without_a_reload`).
  The Node runtime test is skipped locally because `node` is not installed;
  the static ordering test passes.

### 2. MTP is never enabled by the assistant

- **Symptom:** Every assistant measurement/plan sends `mtp: false`, even for
  `-mtp` checkpoints.
- **Evidence:**
  - `POST /admin/api/cluster/models` (the source of `modelOptions`) returns
    `mtp_compatible: None` for all seven local models.
  - `GET /admin/api/models` (same app) returns the correct facts:
    `DeepSeek-V4.1-Flash-1017-oQ2e-ngram-mtp`, `GLM-5.3-Flash-MLX-4bit-MTP`,
    `GLM-5.3-Flash-oQ2e-mtp` and `Qwen3.8-Flash-Next-oQ5e-mtp` are
    `mtp_compatible: true`; the `dev-*` models are false.
  - `assistantMtpFor(modelPath)` reads `this.modelOptions`, not
    `/admin/api/models` or a catalogue field, so it always returns false.
  - `AssistantRecommendRequest` has no `mtp` field; the live recommendation
    reported `"mtp": false`.
- **Impact:** MTP-capable models are planned/started without the draft head;
  the recommendation is also computed without the rank-0 draft reservation.
  A live GLM plan with `mtp: true` needs **3 Macs** at 8k/16k/32k, while the
  MTP-off recommendation claimed **2 Macs** at 32k.
- **Status:** **source fixed, installed in the helper4 build.** The cluster
  model inventory now computes and carries `mtp_compatible` for local and
  remote rows (`mtp_compatible_for_model`), and the merge preserves it. Live
  verification after rollout: `/admin/api/cluster/models` without
  `python_executable` returned all seven models with
  `DeepSeek/GLM/Qwen → true` and `dev-* → false`, `errors: []`. The
  assistant's `assistantMtpFor` now reads a real value. Tests:
  `tests/test_cluster_model_inventory.py`.
- **Remaining follow-up:** `recommend` still takes `mtp` from
  `record.model.mtp` (the entry measurement). If the entry model is not
  MTP-capable but a recommended candidate is, the ranking is computed with
  `mtp: false`; the UI then re-measures that candidate with MTP on and plans
  again. The inventory field alone does not change that ranking.

### 3. Slim app: rank 0 starts without the `omlx` package (P0)

- **Live:** measurement `ms-20261108T182642Z-000c2483` (`dev-1.5b`, 4 Macs),
  plan `736d4831913707f7a8a59bf4d752b3429443b2c58d5e45b244392ed1af651846`
  (2 Macs), apply `op-20261108T182650Z-apply-0001c351` → **applied**.
  Start `op-20261108T182654Z-start-000250f8` → **failed**.
- **Error:** local rank 0 exits with
  `ModuleNotFoundError: No module named 'omlx'` from
  `/Users/andreaskolb/Library/Application Support/oMLX/runtime/venv/bin/python3`.
  The operation also carries a noisy
  `ssh … pid=$(cat None); … rm None` cleanup failure from MLX's launcher.
- **Cause:** `provisioning.py` builds rank 0 with
  `python_executable=None`, on the assumption that rank 0 is the local server
  process. The Tahoe workaround actually spawns rank 0 over SSH to the
  coordinator's own LAN address. The fallback is `sys.executable`, the external
  runtime venv, where `omlx` was uninstalled. Only
  `~/.omlx/bin/omlx-cluster-python` exports
  `PYTHONPATH=/Applications/oMLX.app/Contents/Resources`; rank 0 does not use
  it. Verified live: the shim prints
  `/Applications/oMLX.app/Contents/Resources/omlx/__init__.py`; the venv path
  is the interpreter in the failure.
- **Impact:** every assistant start on the signed slim app fails at rank 0;
  apply still reports `applied`. The final error is mapped to
  `retry_coordinator`, which cannot fix a missing module. This is a DAU blocker
  for the current distribution.
- **Also:** the card's only failed-state action retries the same start; the
  engine pool caches `dev-1.5b` as a failed load until the next discovery
  refresh, and the card has no “reload models” step. A retry alone can loop on
  the cached failure.
- **Status:** **source fixed, installed in the helper4 build; live start
  ready.** `provisioning.py` now sets
  `facts.python_executable or DEFAULT_REMOTE_PYTHON` and resolves it with
  `Path(...).expanduser()` so the deployment contract receives an absolute
  path. The first helper3 live apply after the initial fix failed with
  `cluster host Python executable must be absolute`; helper4 fixed that.
  Tests: `test_a_worker_without_a_reported_interpreter_uses_the_published_shim`
  and the updated `test_the_worker_uses_the_interpreter_it_reported`.

### 4. Remote disk-free is unknown when the model is absent; the DeepSeek 2-Mac plan is therefore not runnable

- **Symptom:** The recommendation/plan treats a Mac that would need a large
  model copy as `can_stage: true` even when its real free space is
  insufficient.
- **Live evidence:**
  - `ms-20261108T182339Z-000b69f6` measured DeepSeek V4.1 on all four Macs.
  - DeepSeek is present only on the local Mac; `.12` has no copy.
  - `GET /assistant/status` for `.12`: `disk_free_gib: null`.
  - `recommend` for DeepSeek: selected `.11` + `.12`; `.12` has
    `disk_free_bytes: null`, `can_stage: true`; selected context 32,768;
    policy Engram table on SSD + 25 % experts resident.
  - Plan `030a041765ea9fce730d968b88c834d3af6a0bfd1f565f78e75a7dd1717cedfb`
    selects local + `.12`, 20 layers per Mac.
  - Actual `.12` free space: `351,798,244 KiB` = **335.5 GiB**.
  - DeepSeek copy size: `384,124,494,288` bytes = **357.7 GiB**.
  - Shortfall: **~22.2 GiB**; `apply` would refuse `insufficient_disk` after
    the plan, not before.
- **Cause:** `staging.free_disk_bytes()` runs `df -k <full model path>` over
  SSH. The model directory does not exist on `.12`, so `df` fails, the
  function returns 0, and `_disk_free()` converts 0 to `None` **without a
  warning**. The election's `NodeFacts.can_stage()` treats unknown free space
  as "not disproven".
- **Status:** **source fixed, installed in the helper4 build.** `staging.free_disk_bytes()`
  now walks up to the nearest existing parent over SSH, and
  `assistant.routes._disk_free()` emits `disk_free_unreadable` instead of
  silently returning `None` for a zero answer. Live verification: the DeepSeek
  recommendation after rollout sees `.12` with **335.0 GiB free** and needs
  **365.2 GiB**, marks `.12` `can_stage: false`, and exposes `insufficient_disk`
  with action `free_disk_space`. Tests:
  `test_remote_free_space_walks_up_to_an_existing_parent`,
  `test_unreadable_free_space_is_reported_not_silently_unknown`.

### 5. Model inventory returns zero models after a reload; legacy Python default

- **Symptom:** `POST /admin/api/cluster/models` returns `models: []` and
  `errors: [{detail: "remote Python executable must be an absolute path"}]`
  when the caller does not pass `python_executable`.
- **Cause:** the route defaults to
  `"~/omlx-distributed/.venv/bin/python"`; the remote inventory rejects a
  non-absolute explicit path. The app's published shim is
  `~/.omlx/bin/omlx-cluster-python` (`DEFAULT_REMOTE_PYTHON`).
- **Why live:** the UI fills `python_executable` from
  `checks.probes[peer].result.status.runtime.python_executable`. After a page
  reload the checks have not run, so `inventoryHosts()` / `assistantNodes()`
  send no value and the model list is empty. `loadModels()` ignores the
  response's `errors`, so the user only sees an empty list.
- **Status:** **source fixed, installed in the helper4 build.** The route
  default is now `DEFAULT_REMOTE_PYTHON` (`~/.omlx/bin/omlx-cluster-python`).
  Live verification without `python_executable` returned all models and
  `errors: []`. Test:
  `test_cluster_inventory_defaults_to_the_published_worker_shim`.

### 6. A changed SSH host key is a dead end in the pairing UI

- **Symptom:** after a peer reinstall/key change, pairing fails with
  `SSH enrollment failed; peer was not paired: refusing changed SSH host key
  for enrolled worker 172.16.1.14`.
- **What we had to do:** on the local Mac and the peers, run
  `ssh-keygen -R` for `.12`/`.13`/`.14` (and `.11` on the peers), then pair
  again. Backups are `~/.ssh/known_hosts.old`.
- **Impact:** the fail-closed rule is correct, but there is no explicit
  “trust the new key / forget the old enrollment” action in the UI. A
  reflashed or renamed Mac cannot be paired without shell access.
- **Status:** open UX/product decision. Do not weaken the pin silently.

## P2 — misleading or inconsistent output

### 7. Recommendation “staging_required” names excluded Macs

- **Evidence:** DeepSeek recommendation (selected `.11` + `.12`) says
  “357.7 GiB has to be copied to **82b7…(.13), a6c9…(.12), c848…(.14)**”,
  while `excluded_nodes` contains `.13` and `.14`.
- **Cause:** `recommendation._feasible_warnings()` receives staging rows for
  every measured node; it is not filtered to `selected.rank_order`.
- **Impact:** the user may free disk on Macs the plan will never write.
  Excluded Macs are never staged/applied (the frozen rule).
- **Status:** **source fixed, installed in the helper4 build.** `_recommend_one()`
  filters the staging rows to `selected.rank_order` before building warnings.
  Live verification: the DeepSeek recommendation names only `.12` (the selected
  destination) in `staging_required`; `.13`/`.14` are excluded and not named.
  Test: `test_staging_warning_only_names_selected_macs`.

### 8. Pending-approval `addrs` is a list of strings, not address objects

- **Evidence:** `pairing.py` `PendingRequest.to_dict()` emits
  `"addrs": list(self.addrs)` (`list[str]`), while discovery rows use
  `local_addr_dicts()` and the devices contract uses
  `[{"ip": ..., "if_type": ...}]`. The devices route merges the pending row
  into the discovered row, so the `addrs` shape changes for an
  `awaiting_approval` device.
- **Impact:** address consumers (`bestDeviceAddr`, link/transport labels)
  silently see no addresses for that row. The approval code input itself does
  not need the address, but the schema is inconsistent.
- **Status:** **source fixed, installed in the helper4 build.**
  `discovery_routes._address_rows()` normalizes pending strings to
  `{"ip": ..., "if_type": "unknown"}`; the existing pending-request tests now
  assert the merged shape. Not re-tested against a live pending request after
  rollout.
