## 2. Critical findings (verified, P0)

### B1 — The chat profile overwrites the user's sampling values on every start

`start.py:1699` checks `entry.get("temperature")` etc. at the **top level** —
but the real catalogue (`admin/routes.py:2623`) nests them under
`entry["settings"]` (`asdict(settings)`; `_model_options` puts no sampling
keys at the top level). The guard never fires in production, `CHAT_PROFILE`
is written on every start, and the settings PUT (`admin/routes.py:2852`)
merges field by field → e.g. a user temperature of 0.2 becomes 0.6.
**Violates the frozen invariant "never overwrites a value the user set".**
The tests pass only because the fakes encode the wrong shape
(`tests/cluster_assistant/assistant_harness.py:301`,
`test_start_api.py:657/684`) — classic fake drift.

Fix: read the guard from `entry.get("settings", {})`, fill per key instead of
`any()`, align the fakes with the real catalogue shape.

### B2 — Every apply/start unloads all loaded models on the coordinator

`start.py:660` and `start.py:1005` call `ops.reload()` unconditionally →
`_reload_models()` → `_apply_model_dirs_runtime()` → "Unload all loaded
models" + `pool._entries.clear()` (`admin/routes.py:1357/1394`). A chat model
the user is running in parallel is evicted mid-use.

Fix: skip the reload when the target model is already listed
(`_model_entry`, `start.py:1315`).

### B3 — The assistant card vanishes as soon as any deployment exists — including its own

The whole card (incl. ready/stop/endpoint/Open Chat) lives **only** inside the
`wizardState() === 'plan'` section (`_cluster_v2.html:820–1367`); the `active`
section (1711) contains none of it. `wizardState()` checks
`configuredDeployment()` first (`cluster_v2.js:1239`), which falls back to
`deployments[0]` (`cluster_v2.js:813`). Consequence: on any Mac with a saved
setup the assistant is **unreachable at all**; after its own start the card
hides mid-loading/ready — stop, endpoint, Open Chat and the observed block
become unreachable in exactly the states they exist for.

Fix: lift the card out of the state-gated sections into an always-mounted
block (its own state machine already exists; no `WIZARD_STATES` change).

### B4 — The settings-file fallback can wipe all model settings on a Mac

`provisioning.py:299–354`: hardcoded `~/.omlx/model_settings.json` (local and
in the remote snippet; ignores `OMLX_BASE_PATH`/bootstrap → the policy is
silently not applied on moved data roots), and
`except Exception: document={'version':1,'models':{}}` — **any** read error
(permissions, briefly corrupt JSON) replaces the whole file. Plus a fixed
`.tmp` name (race).

Fix: resolve the path from the server configuration, abort on a read error
instead of resetting, use a unique temp name.

### B5 — The cluster-wide lock has a hole on remote starts

`_remote_ops` (`start.py:283–374`) drives the coordinator's **raw** routes
(`/plan`, `/stage`, `/deployments`) and never creates an assistant operation
record there. The coordinator therefore answers `operations/active` with
`null` while it is working → a second origin can apply/start concurrently.
The frozen rule "one apply/start at a time, cluster-wide" holds per origin
only.

Fix: create/update the operation record on the coordinator through the admin
seam (or serve the lock route there). Test gap: a two-origin lock test would
fail today.

### B6 — A store write failure wedges the assistant permanently

`state.py:748–755` rolls back the terminal state on a save failure;
`routes.py:731` swallows `OSError`; `start.py:1228` catches only `KeyError`.
An unwritable store directory → every operation ends in an inconsistent
state with no way out.

Fix: do not roll back the terminal state; surface a save failure as an
explicit `failed` state with the action `diagnostics`.

### B7 — `OperationStore.applied()` returns the oldest match

`operations.py:856–881` iterates forward; `latest_session` uses `reversed`.
Resume/stop can therefore target a stale apply operation.

Fix: search backwards like `latest_session`.

### U1 — Template syntax error: uncaught exception on every dashboard load

`_cluster_v2.html:1302`:
`x-text="(assistant.networkPreflight?.warnings || []).join(' ')'"` —
a stray quote leaves the expression unterminated (reproduced: `SyntaxError`).
Alpine initializes `x-text` even inside `x-show=false` subtrees → an error on
every page; the network-preflight warnings (a safety-review surface) never
render.

Fix: one character (`.join(' ')`). Plus a static test that parses **every**
binding expression with `new Function(...)` — today's tests only grep
substrings.

### U2 — The measurement 409 is a dead end

A network error during measurement → `failed` with action `measure` →
`resetAssistant()` clears the `measurementId` → the backend answers
`409 measurement_in_progress` **with `measurement_id` and action `status`**
(`routes.py:610–622`) → `failAssistantFrom` (`cluster_v2.js:5649`) adopts only
`operation_id`, never `measurement_id` → `status` does nothing (0 new timers,
runtime-verified). Only a reload escapes.

Fix: adopt `payload.measurement_id`; the `measure` action resumes a named
running measurement instead of resetting. Runtime test mirroring the existing
`operation_in_progress` resume test (`test_cluster_ui_integration_ui.py:953`).

## 4. Efficiency proposals (with A/B numbers)

1. **Move the solver off the event loop**: `plan`/apply re-election/busy
   checks into `asyncio.to_thread` (the pattern exists in `recommend`).
   Worst case today: 2.26 s blocking per recommend, 26,880 `plan_hybrid`
   calls.
2. **Reduce the solver search cost**: early candidate filter (a model that
   cannot fit the summed admission is never enumerated), bisect the context
   ladder instead of the linear descent, memoize identical subproblems.
   Target: worst case well under 1 s.
3. **Probe quality instead of new estimators**: raise the GEMV width/
   iterations or move to a bandwidth-bound kernel; until then use the probe
   only as an election tie-break and document its latency nature. (No
   token-rate estimates — frozen.)
4. **Polling overhead**: a visibility gate like `tick()`, a lightweight status
   projection instead of full inventories, a 2–5 s interval with backoff, SSH
   ControlMaster/keepalive, parallelize the sequential policy writes, fetch
   `ops.models()` once per start (today up to 3×). Every staging tick fsyncs
   the whole store (`start.py:889`) and spawns SSH+Python.
5. **Recommendation ranking** from `weight_bytes` to "fits + usable context +
   estimated critical stage" (B11) — otherwise the assistant recommends the
   worse model.

## 5. Quality and test gaps

- **Fake drift is the systemic risk**: B1 exists only because the fakes
  encode an API shape the real server does not have. Countermeasure: contract
  tests against the real route handlers (not only fakes) for the catalogue
  shape, the settings PUT merge, and `operations/active`.
- Backend test gaps T1–T9 (API review), among them: the two-origin lock
  (would fail today), store save failures, `applied()` ordering, the
  measurement one-job check at store level, delete target resolution.
- UI test gaps: the session card has **zero** runtime coverage; no
  measurement-409 recovery test, no 32-candidate boundary test, no
  use-all-Macs test, no double-click test, no resumed-apply-without-plan
  test; `assistantSmallMacNotes` was static-tested only; no template
  expression syntax validation.
- **CI**: the UI runtime suite skips silently without Node (105 tests on this
  Mac) — it should fail, not skip.
- Code hygiene: no TODO/FIXME in the assistant package, 0 `console.log`, 49
  broad `except` (27 routes, 10 start), 6 documented `noqa`.
- Positive: clean architecture, inert measure/recommend/plan,
  generation-guarded polls (correct), main-card endpoint gating correct, no
  XSS surface (`x-text` only), delete affordance and chat preselect
  contract-true, clean Mac app mount (admin+cluster gates), no new
  `WIZARD_STATES` entries.
